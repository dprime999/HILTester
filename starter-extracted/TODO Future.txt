To make this work seamlessly on a local laptop, you need several system-level requirements, software permissions, and architectural configurations beyond just a GitHub account and plugged-in hardware.🔐 1. Windows Host Permissions & SecurityYour application will be modifying system files and running persistent background services.Windows Administrator Privileges: The user launching your installer or app must have local admin rights. This is required to install background Windows services (the GitHub Runner) and write to system environment variables (%PATH%).PowerShell Execution Policy: By default, Windows blocks unverified scripts. Your app will need to programmatically execute Set-ExecutionPolicy RemoteSigned -Scope Process before it can run the silent setup or dependency scripts.Windows Defender / Firewall Exclusions: The local GitHub runner needs to constantly communicate with GitHub over web sockets. Windows Defender or third-party firewalls might flag or block these unrecognized background network streams unless an inbound/outbound rule is added.🔌 2. USB Stack & Driver OverridesWindows handles USB devices very differently than Linux. This is usually the biggest headache for hardware tools.Zadig / WinUSB Drivers: Windows native drivers will prevent tools like openocd from directly accessing an STM32 debugger (like an ST-LINK). Your app or installer must use a tool like libwdi (the engine behind Zadig) to silently swap the target's composite USB driver to WinUSB or Libusb-win32.Exclusive USB Access Allocation: Because the GitHub runner and your manual dashboard will both want to talk to openocd and picotool, your software must handle resource locking. If the runner is running a test and using the USB port, your dashboard needs to lock its "Manual Flash" button to prevent Windows device conflicts.🌐 3. GitHub API Auths & NetworkingTo make the automated repository creation and runner fetching work, your app needs specific access rights.GitHub Personal Access Token (PAT) with Fine-Grained Scopes: A standard login won't suffice. You or your user must generate a token with specific read/write permissions:administration:write (to add, remove, and fetch registration tokens for self-hosted runners)contents:write (to create new repos, initialize git, and add your workflow files)workflows:write (to allow your app to push the .github/workflows/hil.yml file)Persistent Local Credential Storage: You cannot save this raw token in plain text inside your app's folder. You must utilize the native Windows Credential Manager API (via Node/Rust libraries) to securely store and encrypt the token on the user's local profile.⚙️ 4. Build Environment AbstractionsSince your local app is acting as the compiler engine for the runner, the compilation environment must be rock-solid.Pre-configured Environment Paths: Your compilation tools (arm-none-eabi-gcc, make, cmake) cannot rely on the user manually setting up their system paths. Your app needs to inject these temporary binary folder paths directly into the specific command shell instance it spins up.Workspace Isolation: You need a dedicated, locked root directory (e.g., C:\HIL_Workspace\). If the user modifies files in this directory while a GitHub Action runner is mid-build, the build will corrupt. The app must handle folder lock states during active flashes.
