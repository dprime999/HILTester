| Networking & SSH | paramiko | Standard SSH/SFTP library to remotely configure the Raspberry Pi and run commands. |
| Local Discovery | python-zeroconf | Discovers the Raspberry Pi on the local Wi-Fi/LAN via mDNS without hardcoding IPs. |
| Tailscale Interfacing | Built-in subprocess module | Runs background Windows CLI commands (tailscale status, tailscale up). |
| GitHub Integration | requests or PyGithub | Handles GitHub Device Authorization OAuth flow and repository verification. |
| File Systems & Env | python-dotenv | Reads, modifies, and securely stores project .env configurations and tokens. |
| Async Operations | Built-in asyncio | Keeps the TUI responsive while waiting on slow Docker pulls or SSH operations. |

## Part 2: Step-by-Step Implementation & Delivery Lifecycle## Phase 1: Local TUI App Development

   1. Design the Core State: Establish a local JSON structure to store project configurations, current active network targets, and known hardware baselines.
   2. Build the Backend Engines: Independently script the network discovery engine (Tailscale/mDNS), the GitHub authentication handler, and the SSH Pi automation orchestrator.
   3. Assemble the Textual Interface: Connect the backend engines to interactive TUI screens, ensuring long-running network or hardware tasks execute asynchronously to avoid UI freezing.

## Phase 2: Compilation & Installer Bundling

   1. Compile via PyInstaller: Package your application code, assets, and base Docker image files into a single Windows-compatible directory.
   2. Write the Inno Setup Script (.iss): Create an installation wizard that copies your files to C:\Program Files\HILTester (or a local user directory) and adds a system path/desktop icon shortcut.
   3. Code Sign & Host: Sign the generated installer executable using a code-signing certificate (to bypass Windows SmartScreen warnings) and upload the file directly to your GitHub repository's "Releases" page.

## Phase 3: One-Click End-User Execution Flow

   1. Download & Install: The user downloads your installer, steps through the clean Inno Setup wizard, and receives a dedicated desktop shortcut.
   2. First Boot Initialization: Clicking the desktop icon fires up a terminal window running your unified Textual TUI, immediately dropping the user into the project configuration lifecycle.

## Part 3: TUI Screen-by-Screen Architecture## Screen 1: Project Initialization & Hardware Baseline

* Purpose: Sets the foundation for the HIL workspace.
* Functional Logic:
* Displays a menu prompting: [Create New Project] or [Load Existing Project].
   * Provides a toggle checklist detailing supported hardware signatures (Raspberry Pi, USB Hub, Raspberry Pi Pico, STM32 DUT, Mouse/Keyboard, Monitor).
   * Generates an internal hardware_profile.json baseline representing the exact equipment the test sequence should expect to find.

## Screen 2: Host & Target Network Commissioning

* Purpose: Establishes a rock-solid communication channel to the HIL test PC.
* Functional Logic:
* Checks local network adapters and triggers a ping scan/mDNS inquiry searching for a connected Raspberry Pi.
   * If the device is unfound, invokes tailscale status. If Tailscale is offline or missing, drops into a specialized setup wizard guiding the user through joining their secure Tailnet.
   * Displays a live status dashboard: [LAN Status: Offline] | [Tailscale Status: Connected (IP: 100.X.X.X)].

## Screen 3: Source Control & GitHub OAuth

* Purpose: Links local environment contexts to the remote Git workspace securely.
* Functional Logic:
* Implements the GitHub Device Flow. The TUI presents an alphanumeric code (e.g., ABCD-1234) and a button to open a web browser to ://github.com.
   * Polls the GitHub API asynchronously until the user authenticates, returning a secure token.
   * Scans the workspace directory; if a local clone of dprime999/HILTester doesn't exist, it clones it down automatically.
   * Opens interactive configuration inputs to populate the local .env variables safely without exposing plain-text keys.

## Screen 4: Advanced Hardware Topology Configuration

* Purpose: Accommodates complex testing architectures beyond a single standard board.
* Functional Logic:
* Allows users to interactively declare their exact rig topology (e.g., stacking 3 Picos, 2 STM32 targets, or daisy-chained USB Hubs).
   * Alternative Input Method: Offers an [Import topology.json] shortcut button, bypassing UI forms by accepting an explicitly structured configuration file directly from the user's disk.

## Screen 5: One-Click HIL Pi Deployer

* Purpose: The zero-to-HIL orchestration machine.
* Functional Logic:
* Establishes a remote SSH connection to the targeted Pi.
   * Inspects the environment: verifies if Docker is installed. If missing, sequentially pipe-installs it completely over SSH.
   * Executes a remote lsusb matching command, validating that the physically attached hardware matches the profile created on Screen 1.
   * Pulls the required container image from your registry and boots up the active, network-linked HIL testing runtime environment.

## Screen 6: Testing Control Room (Work in Progress)

* Purpose: Real-time test loop visualization and manipulation.
* Functional Logic:
* Features high-visibility [START TEST] and [STOP TEST] operational controls.
   * Emits an interactive progress bar and log stream console displaying raw loop telemetry.
   * Includes empty placeholder components specifically mapped for future integration with UART streams, JSON payloads, and logic analyzer metrics.

## Screen 7: Failsafe & System Resiliency Monitor

* Purpose: Guards against system crashes, hardware disconnects, or sudden power drops.
* Functional Logic:
* Spawns a background heartbeat thread pinging the Pi and parsing device connectivity indexes continuously.
   * If a disconnect is intercepted, the TUI immediately freezes execution loops, moves the software state into an absolute safety fallback routine, and outputs a diagnostic log containing exact error timestamps.

## Screen 8: Integrated Workspace IDE Integrator

* Purpose: Bridges the gap between your dashboard environment and custom source code adjustments.
* Functional Logic:
* Includes a shortcut command key or button labeled [Open Workspace in Editor].
   * Programmatically searches the host Windows registry for installations of VS Code (code) or Notepad (notepad.exe).
   * Spawns the external text editing program pointed directly at the cloned repository's test directories, intentionally restricting view permissions or hiding infrastructure configurations (like Docker files) unless the user specifically toggles an [Advanced Mode] flag in the TUI settings.

## Screen 9: Knowledge Base & Quickstart Manual

* Purpose: Onboarding reference documentation.
* Functional Logic:
* Utilizes Textual's markdown rendering widget to display an embedded, scannable copy of the product README.md.
   * Outlines foundational capabilities, core problems solved by the HIL rig, target hardware architectures, and a 2-minute quick-start demonstration checklist.
